# 多工作台设计

日期：2026-03-13
范围：Workbench 从单一工作区升级为“轻量多工作台”
状态：Approved

## 1. 背景

当前 `workbench` 只有一个统一池子，所有中短期待处理内容都通过 `pin -> is_pinned` 进入同一个区域。这个模型在早期足够简单，但已经暴露出两个问题：

1. 不同任务语境会互相污染，工作区逐渐退化成“另一个杂物池”。
2. 标签和筛选只能解决“怎么找”，不能解决“现在到底在处理哪件事”。

本次需求的核心不是再增加一种标签，也不是把收藏区再复制一份，而是让用户可以在多个任务上下文之间快速切换，并让每个上下文看到的是一组独立的暂存内容。

## 2. 目标与非目标

### 2.1 目标

1. 将当前单一 `workbench` 升级为多个可切换的工作台。
2. 默认只展示当前工作台内容，不再展示所有工作台合并结果。
3. 保持 `workbench = 中短期处理区`、`collection = 长期保留`、`tag = 内容描述` 三套语义稳定。
4. 让“内容加入了哪个工作台”对用户始终可感知。
5. 保持 mini 模式和正常模式都可用，不引入高密度顶部拥挤问题。

### 2.2 非目标

1. 第一版不支持一个条目同时属于多个工作台。
2. 第一版不支持自动规则分流，不做“命中关键词自动进入某工作台”。
3. 第一版不支持颜色、图标、层级、模板、权限等扩展管理能力。
4. 第一版不让工作台替代标签、收藏或笔记系统。

## 3. 产品定义

### 3.1 核心定义

- `history`：原始历史流。
- `collection`：长期保留区，语义仍然绑定 `favorite`。
- `workbench`：中短期处理区，语义仍然绑定 `pin`。
- `workbench item membership`：一个条目当前属于哪个工作台。

### 3.2 为什么不是标签增强

标签表达的是“内容是什么”或“内容带什么描述”，而工作台表达的是“我现在正拿这条内容做什么”。这两者属于不同层级：

- 标签适合跨视图复用、长期存在、数量可多。
- 工作台适合任务语境切换、短中期使用、数量必须少。

因此本次不把需求落成新的“更大类型字段”或“另一种标签”。

### 3.3 第一版工作台规则

1. 用户拥有多个工作台。
2. 永远存在一个 `默认工作台`，不可删除。
3. 默认打开工作区时，只看到当前工作台内容。
4. 工作台数量上限为 `5`。
5. 第一版一个条目同一时刻只属于一个工作台。
6. 条目一旦进入任意工作台，仍保持 `pin/workbench` 语义。

## 4. 数据模型方案

### 4.1 推荐模型

新增独立工作台实体，而不是仅给条目补一个文本标签。

建议新增：

1. `workbenches`
2. `clipboard_items.workbench_id`

建议字段：

`workbenches`
- `id`
- `name`
- `is_default`
- `sort_order`
- `created_at`
- `updated_at`

`clipboard_items`
- 保留现有 `is_pinned`
- 新增 `workbench_id TEXT NULL`

### 4.2 兼容语义

第一版保持以下兼容规则：

1. `workbench_id IS NOT NULL` 的条目，视为在某个工作台中。
2. 在第一版里，`workbench_id IS NOT NULL` 时，`is_pinned` 必须为 `1`。
3. 当条目移出工作台时，同时清空 `workbench_id` 并将 `is_pinned` 置为 `0`。
4. 历史代码中依赖 `is_pinned` 的逻辑先不一次性移除，而是逐步迁移到“当前工作台 + workbench_id”模型。

这样做的原因是：

- 能在不推翻现有 `pin <-> workbench` 命名约束的前提下完成升级。
- 可以减少首轮改造范围，避免一次性冲击所有 UI 与命令。

### 4.3 默认迁移策略

数据库迁移时：

1. 创建 `workbenches` 表。
2. 自动创建一个 `默认工作台`。
3. 为所有当前 `is_pinned = 1` 的旧条目回填 `workbench_id = default_workbench_id`。
4. 旧数据迁移完成后，工作区首屏直接显示默认工作台内容。

## 5. 核心交互设计

### 5.1 顶部入口

工作区顶部新增一行独立的工作台头部，不放入现有筛选栏。

结构：

- 左侧：当前工作台名称胶囊，例如 `博客评论 ▾`
- 右侧：`+` 新建工作台

原因：

1. 当前筛选栏已经拥挤，尤其 mini 模式下会自动折叠为图标态。
2. “切换工作台”属于切换上下文，不属于筛选当前列表，层级应高于筛选栏。
3. 用户必须一眼知道“当前正在往哪个工作台里加内容”。

### 5.2 工作台切换器

第一版采用“当前工作台胶囊 + 点击展开列表”的轻量方案。

正常模式：

- 点击当前工作台胶囊，打开 popover 下拉列表。
- 列表展示所有工作台，当前项有明显选中态。
- 列表底部提供 `新建工作台`。
- 记住用户最后一次选中的工作台；下次打开应用时优先恢复，失效时回退到 `默认工作台`。

mini 模式：

- 点击当前工作台胶囊，打开全宽 popover 或底部抽屉。
- 不使用横向 tabs，避免在 `320x450` 下挤占顶部空间。

### 5.3 工作台管理规则

1. 可创建自定义名称工作台。
2. `默认工作台` 不可删除。
3. 非默认工作台可重命名。
4. 非默认工作台可删除。
5. 删除非默认工作台时，其内容自动迁移到 `默认工作台`，并给出明确确认与反馈。

不采用“只允许删除空工作台”的原因是操作链路过硬，容易让工作台管理变成负担。

### 5.4 内容进入哪个工作台

第一版统一规则如下：

1. 当前正停留在某个工作台时，从历史流显式执行 `pin / add to workbench`，内容进入当前工作台。
2. 在某个工作台内创建快捷笔记，内容进入当前工作台。
3. 在某个工作台上下文里触发快速输出，产物进入当前工作台。
4. 无明确上下文的工作区写入动作，进入 `默认工作台`。

无明确上下文包括但不限于：

- 全局快捷输入
- 外部入口
- 尚未进入具体工作台上下文的默认写入路径

### 5.5 内容归属反馈

每次加入工作台后，提示必须包含目标工作台名，不能只提示“已加入工作区”。

示例：

- `已加入“博客评论”工作台`
- `已加入默认工作台`

反馈建议提供：

1. `切换过去`
2. `撤销`

这样用户不会产生“我刚刚加进去的内容去哪了”的焦虑。

### 5.6 移动与移出

第一版条目只属于一个工作台，因此工作区内相关动作定义如下：

1. `移动到其他工作台`：修改 `workbench_id`。
2. `移出工作区`：清空 `workbench_id`，同时 `is_pinned = 0`。
3. `清空当前工作台`：仅清空当前工作台下条目的工作台归属，不影响其他工作台。
4. `快照 / 导出 / 批量操作`：默认只作用于当前工作台。

## 6. 搜索与筛选

### 6.1 默认搜索作用域

工作区顶部搜索默认只搜索当前工作台。

原因：

1. 多工作台的价值就是语境隔离。
2. 如果默认一搜就跨全部工作台，边界会重新变模糊。

### 6.2 跨工作台搜索兜底

需要支持显式跨工作台搜索，但不能作为默认行为。

推荐交互：

1. 当前工作台搜索无结果时，空态给出 `改为搜索全部工作台` 入口。
2. 或提供一个轻量 scope 切换：`当前工作台 / 全部工作台`。

跨工作台结果必须附带所属工作台标识，并支持点击后直接切换到对应工作台。

### 6.3 后端筛选约束

涉及工作区主列表时，继续遵循“后端筛选优先”：

1. 搜索、类型、标签、日期、收藏等条件仍通过 `search_items + SearchFilters` 下推后端。
2. 新增工作台筛选维度时，应同步扩展 `SearchFilters`，并在仓储 SQL 中确保对当前工作台约束生效。
3. 前端不承担主筛选，只负责展示当前工作台与筛选状态。

## 7. 正常模式与 Mini 模式

### 7.1 正常模式

顶部结构建议为：

1. 工作台头部
2. 快捷笔记
3. 筛选栏
4. 当前工作台内容列表

### 7.2 Mini 模式

必须验证：

1. `320x450`
2. `375x667`
3. `560x700`
4. `800x600`

mini 模式约束：

1. 工作台切换器不做横向多 tab 常驻。
2. 工作台名称胶囊始终可见。
3. 工作台下拉在小窗中使用抽屉式或全宽 popover。
4. 中英文名称都不能挤压成难读布局。

## 8. 错误与降级策略

1. 当前工作台 ID 丢失或失效时，自动回退到 `默认工作台`。
2. 删除工作台后，如果当前选中项已失效，自动切换到 `默认工作台`。
3. 跨工作台搜索失败时，仅影响扩展搜索结果，不阻塞当前工作台浏览。
4. 若工作台创建或重命名失败，保留当前工作台状态并提示具体失败原因。

## 9. 验收点

### 9.1 语义验收

1. `pin` 仍只对应 `workbench`。
2. `favorite` 仍只对应 `collection`。
3. 工作台不是标签，不与标签筛选混用。

### 9.2 功能验收

1. 旧 `is_pinned` 数据升级后全部进入 `默认工作台`。
2. 工作区默认只显示当前工作台内容。
3. 从历史流 pin 到工作区时，内容进入当前工作台。
4. 快捷笔记与快速输出进入当前工作台。
5. 跨工作台搜索能展示归属工作台并支持跳转。

### 9.3 体验验收

1. 用户始终能看见当前工作台名称。
2. 用户每次加入内容后都能知道它进入了哪个工作台。
3. mini 与正常模式下，顶部区域都不发生拥挤失控。

## 10. 分阶段实施建议

### Phase 1

1. 数据迁移：`workbenches + clipboard_items.workbench_id`
2. 顶部工作台切换器
3. 当前工作台内容加载
4. 当前工作台内搜索/筛选
5. pin / 快捷笔记 / 快速输出 写入当前工作台
6. 基础创建、重命名、删除、迁移到默认工作台

### Phase 2

1. 显式 `移动到其他工作台`
2. 跨工作台搜索入口优化
3. 工作台最近使用排序

### Phase 3

仅在真实用户验证有明确需求时再考虑：

1. 一个条目属于多个工作台
2. 自动分流规则
3. 工作台模板、图标、颜色
