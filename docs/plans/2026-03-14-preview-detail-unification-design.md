# 预览详情统一与内容展示收口设计

日期：2026-03-14
范围：将现有“内容展示”独立窗口收口到主窗口 `预览详情` 体系，保留独立编辑窗口
状态：Approved

## 1. 背景

当前仓库内已经存在多条与“查看详情”相关的链路：

1. 主窗口内的 `PreviewPanel`，通过 `panelMode = 'preview'` 承接详情浏览。
2. 历史流内联展开的 `InlinePreviewPanel`。
3. hover 预览与图片 lightbox。
4. 额外通过 `WebviewWindow` 打开的“内容展示”独立预览窗口。

这些能力虽然都在解决“查看内容细节”问题，但入口、命名和承载容器并不统一。对用户来说，同样是“看详情”，有时会进入主窗口右侧预览，有时又会弹出一个单独窗口，心智负担偏重，也削弱了主窗口预览体系的连续性。

目前更合理的方向不是再新增一套详情壳，而是承认主窗口 `预览详情` 已经是正确主线，并把“内容展示”这层额外语义收掉。

## 2. 目标与非目标

### 2.1 目标

1. `预览详情` 成为唯一的详情浏览入口。
2. 现有“内容展示”相关入口统一改走主窗口内预览链路。
3. 历史流、收藏区、工作区点击详情时，进入体验与返回语义保持一致。
4. normal 与 mini 模式下都沿用同一套预览心智，不再出现同类内容跳去独立 webview 的情况。
5. 保持图片、文本、链接、文件等内容类型的预览能力不回退。

### 2.2 非目标

1. 本次不重做 `PreviewPanel` 的视觉风格，只做体系收口与入口统一。
2. 本次不改数据模型，不改历史流 / 收藏区 / 工作区的数据来源。
3. 本次不移除 `HistoryEditorWindow`，它继续作为深度编辑窗口存在。
4. 本次不把所有弹层都改成和 `QuickNoteOverlay` 完全同构的视觉样式。
5. 本次不顺手重构 hover 预览与内联预览的所有细节，只要求它们与主预览语义对齐。

## 3. 方案结论

本次采用以下最终方案：

1. 删除“内容展示”作为独立产品概念。
2. 用户侧统一只保留一个详情语义：`预览详情`。
3. 普通详情浏览统一进入主窗口 `PreviewPanel` 体系，不再新开“内容展示” webview。
4. `HistoryEditorWindow` 暂时保留，明确定位为“编辑”，不再承担普通浏览延伸职责。
5. 借鉴 `QuickNoteOverlay` 的不是视觉造型，而是“应用内承接、避免额外窗口跳出”的交互原则。

该方案是当前最稳妥的中间路径：

1. 比“只删一个窗口”更统一，不会继续保留双轨心智。
2. 比“把所有编辑窗都收回主窗口”更稳，回归面更可控。
3. 能复用现有 `PreviewPanel`、`panelMode` 和返回链路，不需要重新发明主预览容器。

## 4. 语义收口

### 4.1 产品语义

收口后仅保留两层清晰语义：

1. `预览详情`：负责查看内容、执行基础操作。
2. `编辑`：负责修改内容、备注、标签等深度操作。

### 4.2 命名原则

1. 所有原“内容展示”文案统一收口为“预览详情”。
2. 所有仅用于打开独立预览窗口的函数、日志与提示，后续迁移时应改名或下线，避免残留旧概念。
3. “预览”与“编辑”必须继续分离，不能把两者重新混成一个弹层。

### 4.3 用户心智

用户收口后的默认理解应当是：

1. 点击卡片或详情入口，就是进入 `预览详情`。
2. 在 `预览详情` 内可复制、收藏、置顶、打开原内容、查看图片等。
3. 当需要修改正文或做重编辑时，再进入编辑能力。

## 5. 入口与交互规则

### 5.1 统一入口

以下区域进入详情时，统一落到主窗口 `预览详情`：

1. 历史流卡片详情入口。
2. 收藏区卡片详情入口。
3. 工作区卡片详情入口。
4. 现有所有会打开“内容展示”独立窗口的普通预览入口。

### 5.2 返回规则

从哪个区域进入，就从哪个区域返回：

1. 从历史流进入，关闭后回历史流上下文。
2. 从收藏区进入，关闭后回收藏区上下文。
3. 从工作区进入，关闭后回工作区上下文。
4. 若从对比态进入预览，则继续沿用现有 compare -> preview -> compare 的返回语义。

### 5.3 normal / mini 规则

1. normal 模式继续以主窗口 `PreviewPanel` 作为详情宿主。
2. mini 模式也走同一条预览语义链路，不再因为内容类型不同而跳转独立预览窗。
3. mini 与正常模式允许布局密度不同，但不允许详情入口语义不同。

### 5.4 类型能力要求

以下能力在收口后必须继续可用：

1. 文本内容浏览、复制、打开链接。
2. 图片查看、lightbox 放大、相关快捷操作。
3. 文件内容预览、文件打开、在文件夹中显示。
4. 链接元信息展示与打开行为。

## 6. 架构与职责划分

### 6.1 主详情宿主

主窗口 `PreviewPanel` 作为唯一详情宿主，继续负责：

1. 内容类型差异展示。
2. 基础操作按钮。
3. 返回上下文管理。
4. 标签、备注、附加工具能力。

### 6.2 状态入口

`panelMode = 'preview'` 继续作为唯一详情状态入口：

1. 各区域卡片只负责触发进入预览。
2. 具体显示逻辑统一收口到 `PreviewPanel`。
3. 不允许卡片组件继续各自分叉出新的独立预览容器。

### 6.3 服务边界

`windowService` 的后续职责应收敛为：

1. 保留真正需要独立窗口的能力，如 `HistoryEditorWindow`、widget、快速记录窗口。
2. 逐步下线仅用于“内容展示”独立预览的窗口服务。

### 6.4 编辑边界

`HistoryEditorWindow` 暂时不并入这次收口，原因如下：

1. 它已经具备独立尺寸记忆、窗口置顶、自动保存等完整编辑链路。
2. 它不是普通浏览容器，而是重编辑容器。
3. 若本次强行一并收回主窗口，会显著扩大回归面。

## 7. 迁移顺序

本次建议按两步走：

### 7.1 第一步：语义与入口收口

1. 去掉“内容展示”作为对外概念。
2. 将相关入口统一改走主窗口 `预览详情`。
3. 确保各区域进入与返回语义稳定。

### 7.2 第二步：窗口服务清理

1. 清理 `windowService` 中仅为“内容展示”服务的分支。
2. 清理相关 i18n 文案、日志和命名残留。
3. 只保留真正需要独立窗口的能力。

这样可以先解决用户体验分裂问题，再做技术层收尾，降低一次性改动风险。

## 8. 风险点

### 8.1 返回链路错乱

如果进入预览后关闭时没有准确回到原区域，会直接破坏三大区域的连续体验。

### 8.2 mini / 正常模式分叉

如果 normal 模式走 `PreviewPanel`，mini 模式却仍保留独立窗口或另一套逻辑，就等于收口失败。

### 8.3 内容类型能力回退

若图片 lightbox、文件预览、链接打开等能力在收口时缺失，会让“统一”变成退化。

### 8.4 命名残留

若 UI、i18n、服务函数中继续残留“内容展示”，后续协作时会持续污染设计语义。

## 9. 验收标准

1. 历史流、收藏区、工作区进入详情时，统一进入 `预览详情`。
2. 不再出现新的“内容展示”独立 webview 作为普通详情浏览入口。
3. 关闭预览后，能正确回到进入前的历史流 / 收藏区 / 工作区 / 对比态上下文。
4. 图片、文本、链接、文件四类内容的主路径能力保持可用。
5. `320x450`、`375x667`、`560x700`、`800x600` 下都能完成进入、返回、滚动与主操作。
6. `HistoryEditorWindow` 仍可作为深度编辑入口独立使用，不受本次收口影响。

## 10. 后续实施建议

实施时建议优先检查以下代码边界：

1. `previewInteractionPolicy` 与各卡片点击链路是否仍有分叉到独立窗口。
2. `windowService` 中“内容展示”预览窗口的调用点是否已全部迁移。
3. `PreviewPanel` 在 normal / mini / 收藏区 / 工作区下的返回语义是否一致。
4. i18n 中“内容展示”相关文案是否全部改为 `预览详情` 或等价统一文案。

本设计通过后，后续实施应优先保证“统一入口 + 返回一致 + mini / normal 一致”，再处理命名清理和服务下线。
