# AI 搜索设计

## 背景

当前 Qollect 已有一条较成熟的普通搜索链路：

1. 前端提交搜索词与筛选条件。
2. 后端通过 `search_items + SearchFilters` 下推到仓储层。
3. 仓储层以 `FTS + LIKE + SearchFilters` 组合完成主检索。

这条链路在“明确关键词 + 明确筛选条件”的场景下已经足够稳定，但在以下场景体验偏弱：

- 用户只能模糊回忆内容，不知道准确关键词。
- 用户用自然语言表达，例如“上周那段 Python 正则”。
- 用户希望按语义意图搜索，而不是纯字面匹配。
- 用户希望跨历史流、收藏区、工作区做全局回忆式查找。

本设计的目标不是向量化，也不是让 AI 直接执行 SQL，而是在不破坏现有后端搜索主链的前提下，为用户增加一个单独的 `AI 搜索` 入口，让 AI 负责：

1. 理解自然语言问题。
2. 生成结构化检索计划。
3. 对已有搜索候选做相关性重排与一句话总结。

## 目标

### 产品目标

1. 新增一个单独的 `AI 搜索` 入口，不替代普通搜索。
2. 默认搜索范围为全局，而不是当前视图。
3. 返回形式保持“搜索产品”语义，而不是聊天产品语义：
   - 一句简短总结
   - 结果列表
4. 让用户能直接问：
   - `帮我找上周复制过的 Python 正则`
   - `找一下微信里复制过的那段链接`
   - `找图片里有订单号的内容`

### 技术目标

1. 继续复用现有 `search_items + SearchFilters` 链路。
2. AI 不直接访问 SQLite。
3. AI 不直接生成 SQL。
4. 失败时可稳定降级为普通搜索，不出现“AI 一坏整条搜索不可用”。

## 非目标

V1 明确不做以下内容：

1. 不做向量数据库。
2. 不做 embedding。
3. 不做多轮对话式搜索会话。
4. 不做 AI 自由执行 SQL。
5. 不替换普通搜索框。
6. 不在 V1 中引入新的数据库字段或新索引结构。

## 用户体验

## 入口

在现有搜索附近新增一个单独的 `AI 搜索` 入口。

交互原则：

1. 普通搜索继续保持即时、快速、可预测。
2. `AI 搜索` 明确是“慢一点但更会理解问题”的增强入口。
3. 不复用普通搜索框，避免用户误以为所有搜索都会触发 AI。

## 面板形态

点击 `AI 搜索` 后，打开单独输入区或轻量弹层。

建议文案：

- 标题：`AI 搜索`
- 占位：`问我你之前复制过什么，例如：上周那段 Python 正则`
- 范围提示：`搜索范围：全部内容`

## 返回结果

V1 只展示两层内容：

1. 一句简短总结。
2. 搜索结果列表。

不展示长篇 AI 回答，不展示聊天气泡，不做连续追问。

可选折叠区：

- 已理解为的搜索词
- 已应用的筛选条件

这样既能帮助用户理解 AI 在做什么，也不会让界面变成调试面板。

## 状态反馈

建议显示三段状态：

1. `正在理解问题`
2. `正在搜索候选`
3. `正在整理结果`

这样可以让用户明确感知延迟来自哪里，而不是只看到一个长时间转圈。

## 总体架构

AI 搜索使用“两阶段 AI + 一阶段现有检索”的保守结构：

1. AI 意图解析
2. 后端候选检索
3. AI 重排与一句话总结

核心原则：

1. AI 负责理解与排序。
2. 搜索主链继续由现有后端掌控。
3. 数据库访问保持在后端既有仓储层中完成。

## 阶段一：AI 意图解析

### 定位

第一阶段不是聊天回答，而是一个受约束的 `Search Planner`。

其职责是把用户自然语言翻译成一个结构化检索计划。

### 输入

- 用户输入的自然语言问题
- 可选的当前时间上下文
- 可选的产品规则说明

### 输出结构

建议定义一个专门的规划结构，例如：

```ts
type AiSearchPlan = {
  goal: string
  query: string
  filters: SearchFilters
  hints: {
    prefer_recent?: boolean
    prefer_ocr_text?: boolean
    prefer_note?: boolean
    prefer_code?: boolean
  }
  reason?: string
}
```

### 识别重点

V1 要重点识别以下五类意图：

1. 时间意图
   - 昨天、最近、上周、上个月、前几天
   - 尽可能转成 `date_range`

2. 内容类型意图
   - 代码、链接、图片、文件、命令、报错
   - 优先映射到 `type_filter` 或 `require_code_language`

3. 来源意图
   - 微信、浏览器、VS Code、终端
   - 优先映射到 `source_filter`

4. 状态意图
   - 收藏过的、钉住的、工作区里的
   - 映射到 `is_favorite`、`is_pinned`、`workbench_id`

5. 语义侧重点
   - 图片里的字
   - 备注里的内容
   - 像正则表达式那样的片段
   - 这类优先进入 `hints`，影响第二阶段重排

### 保守策略

如果 AI 对某个条件不确定，不应强行下严格 filter。

原则：

1. 宁可多召回一点。
2. 也不要在第一阶段就把检索范围缩死。
3. 可以把不确定信息留在 `query` 或 `hints` 里，由第二阶段处理。

## 阶段二：候选检索

### 检索链路

候选检索继续复用现有：

- `search_items`
- `search_items_with_filters`
- `SearchFilters`
- 仓储层 `FTS + LIKE + filter 下推`

这一步不引入新的数据库访问模式。

### 候选数量

V1 建议先取前 `50` 条候选。

理由：

1. 足够让 AI 重排。
2. 避免 token 与延迟快速膨胀。
3. 便于后续逐步调参。

### 轻量化候选

送给第二阶段 AI 的候选不应是完整大对象，而应做轻量裁剪。

建议保留：

- `id`
- `type`
- `content` 预览
- `ocr_text` 预览
- `note` 预览
- `tags`
- `source_app`
- `created_at`
- `is_favorite`
- `is_pinned`

这样可以兼顾判断质量与 token 成本。

## 阶段三：AI 重排与总结

### 目标

第二阶段 AI 不负责重新搜索，只负责：

1. 判断哪些候选更符合用户问题。
2. 对候选做重排。
3. 生成一句简短总结。

### 输入

- 原始用户问题
- 第一阶段生成的 plan
- 第一轮搜索返回的候选轻量列表

### 输出结构

建议结构：

```ts
type AiSearchRerankResult = {
  summary: string
  ordered_ids: string[]
  top_reason?: string
}
```

后端根据 `ordered_ids` 对原候选列表重排，避免 AI 直接篡改业务对象。

### 总结文案原则

总结只允许一句短描述，例如：

- `我优先找了上周的代码类内容，最相关的是这 6 条。`
- `我重点匹配了 OCR 文字和最近时间，下面这些结果最像你要找的内容。`

不生成长文，不生成解释性段落。

## 接口设计

建议新增单独命令，而不是复用普通搜索命令。

例如：

```ts
ai_search_items(question: string, limit?: number) -> AiSearchResponse
```

建议返回结构：

```ts
type AiSearchResponse = {
  summary: string
  interpreted_query: string
  interpreted_filters: SearchFilters
  plan_reason?: string
  items: ClipboardItem[]
  total_candidates: number
  reranked: boolean
  fallback_used: 'none' | 'planner_failed' | 'rerank_failed' | 'search_only'
}
```

字段说明：

1. `summary`
   - 一句总结

2. `interpreted_query`
   - AI 提取出的核心检索词

3. `interpreted_filters`
   - AI 提取出的结构化筛选条件

4. `plan_reason`
   - 调试信息，V1 可选不展示

5. `items`
   - 最终结果列表

6. `total_candidates`
   - 第一轮候选数量

7. `reranked`
   - 是否完成第二轮 AI 重排

8. `fallback_used`
   - 是否发生降级

## 失败回退策略

AI 搜索必须可降级。

### 1. 规划失败

场景：

- AI 未返回合法结构
- JSON 解析失败
- 缺少必要字段

策略：

1. 直接把用户原问题当普通搜索词。
2. 使用默认 `SearchFilters` 搜索。
3. `fallback_used = planner_failed`

### 2. 候选为空

场景：

- AI 下了过窄 filter，导致第一轮 0 结果

策略：

1. 自动放宽一次搜索条件。
2. 保留 `query`
3. 去掉部分严格 filters 后重试

目标：

宁可召回宽一点，也不要轻易给用户“没找到”。

### 3. 重排失败

场景：

- 第二阶段 AI 超时
- 第二阶段 AI 输出非法结果

策略：

1. 直接使用第一轮候选顺序。
2. 返回普通候选结果。
3. `fallback_used = rerank_failed`

## 与现有架构的关系

本设计显式遵守仓库现有约束：

1. 主检索继续后端筛选优先。
2. `SearchFilters` 仍是主筛选输入。
3. 前端不承担主筛选职责。
4. 收藏区、工作区、历史流的既有语义不被改写。

AI 搜索在语义上是一个“全局理解式检索入口”，不是对现有局部筛选体系的替代。

## V1 测试边界

建议至少覆盖以下 6 类问题：

1. 时间类
   - `帮我找昨天复制的命令`

2. 代码类
   - `找一下我之前复制过的 Python 正则`

3. 来源类
   - `找一下微信里复制过的那段链接`

4. 收藏 / 工作区类
   - `找我收藏过的 prompt`
   - `找工作区里那段 SQL`

5. OCR 类
   - `找图片里有订单号的内容`

6. 模糊回忆类
   - `我之前复制过一个关于 tailwind 配色的片段`

## 验收标准

V1 验收以“可用且明显优于普通全文搜”为准，不追求全知全能。

通过标准：

1. AI 搜索入口独立存在，不影响普通搜索速度。
2. 对典型自然语言问题，整体结果优于直接全文搜索。
3. 失败时能稳定降级，不出现空白或不可恢复错误。
4. 不破坏历史流 / 收藏区 / 工作区现有搜索与筛选链路。

## 推荐实施顺序

建议分三步实现：

1. 打通新命令与前端入口
   - 先做单入口、单返回结果区

2. 接入第一阶段 Search Planner
   - 先让自然语言能稳定转为 `query + filters`

3. 接入第二阶段重排与总结
   - 在已有候选上增加相关性排序与一句总结

这样可以尽快验证价值，避免一开始把工程面铺太大。
